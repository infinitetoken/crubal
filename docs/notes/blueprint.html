CRUBAL 2 · settled in review · Oct 13, 2026

The whole system, as settled: seven pieces, three relationships, one engine for any kind

Everything decided in the review is on this page. It is the brief for the written spec. CRUBAL is a universal language and engine for data about any kind of thing. Our catalog is its first package. The JSON form is settled too (section 15); the written spec comes next.

Records, the envelope and the three empties

A record is one thing, with pairs. Its envelope is defined by the core and written by the engine: ID, kind, owner, created and updated times (the JSON form, section 15, adds level, parent, worn classes, parts and the sources map). The envelope carries no source; a package can show it as read-only facets.

product: P-4QX7                        // envelope: id, kind item, owner me
  title: "National Lampoon's Christmas Vacation"
  runtime: 97min  [origin: observed, via: me:ocr]   // sources print only when asked
  videoCodec: _                          // applies, not known yet
  hdrFormats: -                          // does not apply
unit: U-9KD2 of P-4QX7
  condition: VG
  price: 12.50USD

Kinds and the three relationships

A kind is a record's root type, fixed when the record is created. It declares its levels, a base class it always wears, and its schema.org type. Classes then refine it: many, changeable, and each may say which kinds can wear it (for: item). Packages declare kinds, so another adopter can add event or vehicle.

Versions

  • Each level step declares what varies at it. A variant group's forks (edition, size × colour) vary at group → product; unit facets (condition, included) vary at product → unit. Shoppers pick along both.
  • A facet can follow a fork (Label follows Edition, Weight follows Size). Following facets are dependent: filter counts for them are taken together.
  • Overriding happens only where a facet is declared to vary, which replaces unit-override. A shared value is stored once, at the highest level where it's true.
  • A variant group is a level, a record with its own identity: UCP's product, with our product as UCP's variant.

Parts

  • Owned parts (disc 2 of this set, the case) exist only inside their whole and wear their own classes.
  • Shared parts are records of their own, linked in. The Work (the film) is carried by the DVD, the Blu-ray and the 4K. Its values are stored once and read through for display, never copied.
  • A unit mirrors its product's parts: disc 2's condition is a unit facet on that part. This is the Manifest, defined.
  • The DVD and Blu-ray of one film are separate products sharing a Work. "Also on other formats" is a view over products that share the Work, not a variant picker.
4

Facets

Types

text, number, date, yes-no, choice, link, image, and compound: a value made of pairs (Cast, Manifest, audio tracks).

  • A compound's children are real facets, addressed through their parent (cast.character, Audio.language), and they can nest to any depth (manifest[2].audio[1].language).
  • A compound's rows have row keys, so reordering doesn't break an address and two sources can tell whether they mean the same row. A many-valued facet declares whether it's an ordered list (billing order) or a set.
  • A choice list fixed by definition (Blu-ray regions A, B, C) says fixed: yes. Off-list values are contradictions only there (section 10).

Aliases are naming, not rules

  • Key aliases (videoCodec ~codec) and value aliases (16:9 ~16x9 ~Widescreen) mean the same thing always, everywhere, for that facet. They live in the definition.
  • They fold before any rule runs. Stored data never holds an alias, and the printer writes only the real name.
  • The test: if it depends on context, it's a suggest rule. If it's another system's vocabulary, it's a contract value map. If it's the same thing under different facets, it's a shared link (&wd:…).
  • Rules about definitions apply: a key alias can't equal another facet's key or alias, and a value alias can't collide within its facet. A choice facet must have values.
  • Adding an alias is safe. Removing one is safe for stored data but can break imports. Turning a value into an alias of another is a merge, which is breaking.

Identity and versions

  • The key is the identity and never changes. It is written with its owner prefix (me:videoCodec), and inside one's own files the bare key is enough. A rename changes the label, and old spellings become aliases.
  • Each facet, class, rule and contract has its own dated versions, which are immutable. A package version is a frozen set of member versions. Inside a package, everything follows current. Outside adopters pin a package version.
  • Stored values carry no version; migrations keep them current. Short IDs (F-7KQ2) are allowed but not required.
5

Classes and modules

  • Classes compose with uses:; there's no inheritance. A class may narrow what it uses, never widen it. extends remains only for contracts and packages, where it is UCP's word.
  • The authoring gesture is unchanged: you build a module. One setting decides what it becomes:
    • stored under its own key (Cast, Manifest): a compound facet;
    • stored flat under a heading (Optical disc, Dimensions): a class that other classes use.
  • Placement (order, the level that collects a facet, the photo frame) is a class setting. It never holds a facet's type or values, so classes and the dictionary can't disagree.
class: OpticalDisc
  uses: VideoRelease
  facets:
    format{DVD|Blu-ray|4K|HD-DVD}              // narrows
    videoCodec{MPEG-2|H.264|VC-1|HEVC|AV1}
    unit::discCondition{NM|VG|G|F|P} +worst

Rules

Every rule has the same shape: when (a condition, optional) → then (a consequence) at a strength. It can also say for (a class, a level, or everywhere) and because (the reason shown to people).

rule: dvdIsMpeg2
  for: OpticalDisc
  when: format is DVD
  then: videoCodec is MPEG-2
  strength: suggest
  because: DVD-Video is MPEG-2 by standard
StrengthA write that breaks itAn empty value
mustrefused, with the reasoncounts as incomplete
shouldsaved and flaggedflagged
suggestnothing; a person's value winsfilled, with the rule as its source

Words

Conditions use is, in, has, not, and, or, plus before, after, over, under, and ranges with in 1..600. Aggregates use the combine rules: worst of parts.condition.

What rules cover

Rules cover checks, requirements, forbidding, narrowing, fills, derivations (templates only) and rollups. Facet settings are shortcuts that expand to rules, with one engine behind them:

SettingExpands to
required: yesthen: title has · must
range (advisory)then: runtime in 1..300 · should
unique: yesthen: gtin is unique · must (a global rule)
when: (a gate)outside the condition, the facet is - · must
combine:then: condition is worst of parts.condition
class narrowingfor: OpticalDisc then: format in DVD, Blu-ray · must
show:visibility to an audience, as a rule

What makes a rule a rule

  • Pure. It reads values and returns a verdict or a proposed value. It never acts. Anything that isn't a template (prices, AI text) arrives through a contract.
  • Layered. No rule depends on its own effect. A rule set that can't be layered (fills and not chasing each other) is refused at publish.
  • Checked against each other. Two must rules that can't both hold are a publish error.
  • Order-free, except where replace is involved, and the engine says where.
  • Global rules are their own class (unique, catalog membership). They look at many records, so they need indexes.
  • Gate turns off with a value stored: the value is kept, hidden and flagged, never silently dropped.
  • Traceable. Every refusal and fill names its rule.

Contracts

If something only decides, it's a rule. If it moves values or does something, it's a contract. Each system declares one contract and maps only to facets: ten systems need ten maps, not forty-five bridges.

KindValues goExamples
sendout to a systemlabel printer, eBay listing, Merchant feed, structured data
receivein from a systemscanner, eBay catalog, imports, OCR, AI, the SKU allocator, the pricer
storeboth ways, with an object's own columnsLocation, Order
formto a person and backUnitizer, editor, checkout, signup, customer corrections
offer · takebetween owners (section 9)a distributor's catalog, a collector's records
  • Parts: kind, needs, gives, reads/writes/stores (the map; -> maps a value), when, who, version, and for intake absorb, ignore, keep-raw.
  • A contract's needs is a class: the same facet lines and the same narrowing (title$80). "eBay needs Format" is the completeness check pointed at a border.
  • Forms are contracts with a person, so the screen assembles itself from needs, using each facet's control.
  • Running one: check the trigger and permission, check needs, map out, act (the only step with an effect), map back with sources, run rules on what came in, record versions used (UCP's envelope).
  • Contracts chain without knowing each other: one's gives satisfies another's needs.

Auth

  • Authorization is inside CRUBAL. who is a condition over the caller, who is a record, and show rules decide visibility.
  • Authentication is the host's job. Sign-in, OAuth and API keys belong to whatever runs the contracts. A contract declares what the other side requires (auth: oauth2, scope …) and names a credential (credential: ebay-seller), and the host resolves the name.
  • No secret ever appears in CRUBAL text. A package must be publishable as-is.

Provenance and ownership

Every stored value carries three things. The full hop-by-hop chain lives in the owners' signed logs.

FieldHoldsChanges?
originwho first established it, and how: observed (read off a real instance), declared (its maker said so), derived (a rule computed it), reported (a catalog says so, origin unknown)never
viawho you got it from: a person, a contract or a rule, with the run and the intake recordper write
ownerwho controls it nowyes, by adopting
  • Rule or contract? Could the value be produced again, from the record's own values, with the same answer? If yes, a rule produced it, and it can be dropped and rebuilt. If no, a contract did (AI, comps, a drawn SKU), and it's irreplaceable, so it is kept.
  • Inherited and read-through values carry no source on the lower record. Their source lives where they're held.
  • The log is hash-linked and signed per write, like git or Certificate Transparency. There's no consensus, mining or global ledger: every record has an owner, so the owner's log is the truth for their data. One write makes one log entry, however many values it touched.
  • A migration never becomes the source. A person's renamed value is still the person's, with the migration added as a note.

Adopting is ✎ "made your own", the same verb at every scale. A person editing a rollup or fill takes it from the rule. A consumer adopting a value takes it from another owner. Adopting a whole record gives a new record with cloned-from. Terms can forbid it. The trust order is per package, a person first by default, and a facet may override it. Customer corrections are a lower-trust person source and land as suggestions.

Sharing between owners

Everyone owns and publishes their data. The presenter publishes an offer (what, to whom, on what terms). The consumer declares a take (which facets, how they merge, their trust). Only the overlap flows. The gates between them are rules on both contracts, and visibility (public, followers, named parties, private; per record, facet or value) is decided by rules.

ModeCopy?Keeps updating?Controlled after by
dump (clone)yesno, oncethe consumer
observed (follow)no; read-throughyesthe presenter
gathered (subscribe)yesyes; arrives as intakethe consumer; their edits win
controlledyesyesthe presenter's terms: no re-sharing, expiry, revocation
  • Modes are defined by these properties, so a package can name new combinations. The four are the first, not a closed list.
  • Only "observed" is technically enforced. The others are agreements the engine honours, backed by licence and law.
  • Parties use domain-based keys published at a well-known address. Hops can be redacted: a hash stands in, and the chain still verifies.
  • A presenter never overrides a consumer's person-entered values, unless the consumer accepted controlled terms.
  • Optional tools: reconciliation compares datasets and lists differences as conflicts. Consensus is a confidence signal from many independent datasets agreeing. It counts independent origins only (forty clones of one catalog are one vote), weights votes by verified identity and origin type, and is never forced.

Intake: absorbing raw data, or bypassing it

Every object arrives through a receive contract (a minimal one for a dump or legacy data), and the raw payload is kept forever, as received. Then it's folded in a fixed order: the contract's map, then aliases, then shapes. Rules run on the result.

OutcomeWhenWhat happens
absorbedfitslands, with its source
newa value the vocabulary doesn't have yetlands, marked new; goes to vocabulary review (add, alias, or reject)
conflictdisagrees with another source's valuethe trust order picks the current value; the other is kept as an alternative
contradictionit can be shown impossibleparked beside the facet, with its citation
unknownno facet for the keycarried under the source's prefix (ebay:Studio), never interpreted
ignoredthe contract says skip itstays in the intake record only
A contradiction must cite what it contradicts: the facet's type, a must rule, another value on the same object, or another record under a global rule. A new value is vocabulary growth, not a contradiction. Off-list values contradict only a fixed list.
  • Outside a should range, or less precise than wanted: lands, flagged. More precise than the facet keeps: store what the facet keeps; the intake record keeps the rest.
  • More values than pick allows is a contradiction with the definition, and review offers both fixes.
  • Bypass: absorb: no for a whole source, ignore: or keep-raw: for keys.
  • Review is by key across all objects ("ebay:Studio: 40,112 objects, 812 values"). A decision changes a map or the vocabulary, never objects directly. Then held intake records are replayed.
  • New and unknown values are searchable by staff, never shown in customer filters or pages. AI can propose mappings, never apply them.
11

Evidence and observations: data consuming data to validate

An observation is not a value. A value is the current answer. An observation is an evidence-backed claim made on one instance that supports or contradicts the value.

  1. evidence
    Captured from a real instance: a photo, a scan, a disc read, a scale or measure-grid reading. Origin: observed.
  2. measurement
    A receive contract (OCR, barcode, vision, the grid) consumes it and produces a raw reading, kept forever as an intake record.
  3. mapping
    The intake fold turns 97 MIN. into an observation runtime: 97min on that unit.
  4. support goes up
    The unit's observation supports the product's value. This is the third flow on the version relationship: values down, rollups up, support up.
  5. validation
    confirmed (n independent observations agree), contradicted (they disagree, so it becomes a conflict), or unobserved (declared or reported only).
  6. version split
    A consistent cluster of disagreeing units is probably a different version. The engine proposes a new product or fork.
  • Independence counts instances and evidence types, not runs. Two photos of one unit are one witness.
  • Re-measuring the same evidence replaces the earlier reading; raw readings stay for replay.
  • Learned patterns go through review. Rules decide what confirmation is worth: observed can outrank declared for physical facts.
  • It works for any kind: an ID document gives a person's name, an invoice gives a service's lines, end credits give the cast on a Work.

Migrations

A breaking version ships a recipe, and every store restamps with it. Stored data is always current. Mapping on read is banned. Inside a store nothing carries a version. At a border, the envelope names the package version the data was written under, so outside adopters restamp their own data when they upgrade.

ChangeRecipe verbNeeds a person?
rename or merge valuesrename · mergeno
narrow date precision, change unitconvert (stated rounding)no
text → choicemerge + reviewthe leftovers
split a valuesplit when …where no rule decides
lower pickreviewusually
change combine rulerecomputeno
merge facets, move a keymovesometimes

review sends leftovers to a queue and never drops them. Writes that arrive during a long restamp are swept again at the end, or folded through the recipe while the migration is open.

13

Views

Views are the seventh piece: a curated display that data is mapped into. A view is a selection of records (by level, worn classes and a condition, or a hand-made list) given a shape. A shape is a set of display slots filled by -> map lines, exactly like a send contract, so one card serves a catalog, a carousel and search. pin and hide curate on top of the rules. Product pages are page shapes whose slots hold other views ("also on other formats", carousels).

  • Filters are sub-indexes inside their view: buckets (value groups or ranges) are the map shoppers see, and counts follow the other picks. New, unknown and held values are never bucketed.
  • Audiences are few and fixed: public (including crawlers), member, staff, owner, named parties. show rules decide visibility per record, facet and value.
  • Roles are itemized permissions (see, edit, run, review) that sit on top of an audience as a filter. A role narrows its audience and never exceeds it, so roles never touch projections, caches or indexes. Default deny above member; a person's roles add up; who holds a role is data with a source.
  • Search engines: the public projection is the canonical, stored, indexed one. Only filters declared in index get landing pages; every other combination is noindex. Titles point to facets; structured data comes from the kind's schema.org type and same-as.
  • AI is not an audience. An unauthenticated bot is public and a signed-in AI is a caller with roles. What differs is use, so packages and views declare terms per audience (public: search yes, answer yes, train no), which the host turns into robots rules, headers and a terms file. Views can add machine shapes (JSON, JSON-LD, a UCP catalog feed) beside their cards, from the same projection, for agents.
  • Stored and indexed, never derived on read. Each view's read set is worked out at publish; a write to a key in it marks only that record's projection stale. fresh: write rebuilds in the same transaction, fresh: 5m batches.

Marks: one meaning each

A mark means one thing at every level. Shorthand exists only for facet lines, and rules, contracts, views and packages are spelled out in words. A two-character mark is its own mark. Settled changes from draft 0.1:

  • an open list ends in ..., and + is only combine;
  • money is 12.50USD, and $ is only text;
  • levels are unit::condition, and . is only a path;
  • value maps are ->;
  • - stays as "does not apply", is never a list item, and n/a is accepted on input;
  • only : or a colon at the end of a line separates a key from its value;
  • a version is a tail: a space, then / and a date.

The JSON form

The JSON holds the same pairs as the text form, with nothing added. Text and JSON convert into each other without loss, apart from comments. The JSON is what gets stored, sent and signed; the text form is for reading and writing.

The envelope

  • Envelope and values are separate. The top level holds only engine-written fields; data lives under values, so a facet key can never collide with an envelope field.
  • The envelope grows past section 2's list (ID, kind, owner, times) by five fields: level, of (the version parent), wears, parts and sources. A record can't be read without its classes, so wears belongs here, not as a value; who chose a class shows in the log.
  • Units store only what varies at their level. Inherited values are read through, never copied. Owned parts nest inside their whole and wear their own classes; a unit mirrors its product's parts by row key.
  • Keys: bare keys belong to the document's own package. Anyone else's keys carry their prefix, including unknown intake keys (ebay:Studio).

Values

  • The facet types plain values, as in the text form: text and choices are strings, numbers are numbers, yes-no is true/false, and dates are ISO strings carrying their precision (1997, 1997-10, 1997-10-03). The JSON alone doesn't say a value's type; a reader without the definitions keeps the plain value.
  • Tagged objects cover everything JSON lacks. Each has one $ member, and $ can't start a facet key, so tags never collide.
  • JSON null is banned. Tools treat it inconsistently, and the three empties must stay distinct. A missing key means absent.

Lists, rows and addresses

  • A many-valued facet is always an array; the facet says whether it's an ordered list or a set.
  • When a compound declares an identity child (cast → person, a link), the row key is that link's target and is never written; otherwise every row carries a minted $row.
  • Addresses are the same paths everywhere (sources, intake, observations, rules): runtime, cast[wd:Q229048].character, parts[disc1].condition, and list items by value, genres["Holiday"]. Plain lists can't hold duplicates.

Sources

  • Sources sit in a parallel map, not wrapped around each value. values stays clean and printable, and hiding sources is leaving the map out.
  • * is the record's default; a more specific address wins. Sources reach per list item and per compound leaf.
  • via points at a log entry, which holds the who and how (person, contract run or rule), the intake record and the signature. owner is left out when it's the record's owner. One write makes one log entry.

  • Definitions (facet, class, rule, contract, package) are the long form's pairs as a JSON object, the shape lib/crubal/dictionary.ts already bridges. The detail goes in the spec.

Decision log, Oct 13, 2026

  1. Language and scope

  2. CRUBAL is universal and will be packaged and published once there's a solid working copy. Our catalog is its first package.
  3. The engine is universal at the kind level. Commerce is a machinery package attached to kinds, never core.
  4. Seven pieces: data, facets, classes, rules, contracts, views, packages. Each refers only downward.
  5. Marks as in section 14; shorthand is for facet lines only.

  6. Records and relationships

  7. Three empties are data; nullability is rules.
  8. The envelope (ID, kind, owner, times) is core and engine-written, with no source.
  9. Kind is the root type with levels, a base class and a schema.org type. It's fixed; classes are many.
  10. Three structural relationships (version, part, kind). Everything else is a link facet.
  11. Override down levels only where a facet is declared to vary. Forks and follows are level-step declarations. A variant group is a level.
  12. Owned and shared parts. Shared parts are read through. Units mirror their product's parts.
  13. DVD and Blu-ray of one film are separate products sharing a Work.

  14. Facets and classes

  15. The compound type, any depth, row keys, ordered list vs set.
  16. Aliases are naming, fold before rules, and are governed by dictionary rules.
  17. fixed: yes for lists fixed by definition.
  18. The key is identity, with dated versions per piece. A package version is a frozen set.
  19. Classes compose with uses:. Modules author as before and become a compound or a used class.

  20. Rules and contracts

  21. Strengths must, should, suggest. Facet settings are shortcuts for rules, with one engine.
  22. Comparison words and in a..b ranges. Templates are the only computation inside rules.
  23. A contract's needs is a class. Forms are contracts with a person.
  24. Authorization is in CRUBAL, authentication is the host's job, and no secrets appear in text.

  25. Provenance, sharing, intake, evidence, migrations

  26. Every record has an owner. Owner and origin are separate: the owner can change by adopting; the origin never does.
  27. Values carry origin (observed, declared, derived, reported), via and owner. The chain lives in hash-linked, signed logs, with no consensus requirement.
  28. Link, copy, adopt. A copy is always self-contained.
  29. "Generated" splits by reproducibility: rule or contract.
  30. Sharing is offer plus take. Modes are defined by their properties and open-ended. Visibility is by rules. "Controlled" on a copy is an agreement.
  31. Reconciliation and consensus are optional tools. Consensus counts independent origins.
  32. Raw payloads are kept forever. Six intake outcomes. A contradiction must cite what it contradicts. Staff search covers raw values.
  33. Observations are separate from values. Support goes up. Independence counts instances. Validation states, with version-split proposals.
  34. Migrations are recipes, every store restamps, and mapping on read is banned.
  35. Spec it now. ME builds single-owner first, with sharing later on the same storage.

  36. The JSON form, Oct 14, 2026

  37. Sources sit in a parallel map keyed by address, with a * default; they reach list items and compound leaves, and via names a log entry.
  38. $-tagged objects for quantity, money, link, image, the empties and qualified values. JSON null is banned.
  39. The facet types plain values, as in the text form; the JSON alone isn't self-describing.
  40. Money is an exact decimal string with a currency; minor units only at borders that need them.
  41. The envelope adds level, of, wears, parts and sources; values live under values.
  42. Raw payloads are stored as exact bytes with a hash.
  43. RFC 8785 canonical form, sets sorted, for hashing and signing.
  44. Comments are not carried in JSON.

  45. Views, Oct 14, 2026

  46. A view is a selection plus a shape; shapes map facets into display slots like send contracts; pin and hide curate.
  47. Filters are per-view sub-indexes; buckets are the map; counts follow the other picks.
  48. Audiences: public, member, staff, owner, named parties. The public projection is the only stored and indexed one.
  49. Roles are itemized permissions on top of an audience, narrowing only; they never affect the machinery.
  50. Only declared filters get indexable landing pages; everything else is noindex.
  51. Projections are stored; the read set decides staleness; fresh picks same-transaction or batched.
  52. AI gets no audience: terms per audience say how what's shown may be used, and machine shapes serve agents from the same projection.

  53. Harvest from the first CRUBAL, Oct 14, 2026

  54. Part slots itemize by default; only fungible: yes may count. Incoming rows and parts are matched (identity, then match, then review) before new rows are minted.
  55. A core notables compound holds per-record facts no class asks for; recurring keys are proposed as facets.
  56. Facets and classes have a lifecycle: candidate, active, retired. The agent advises; a person promotes.
  57. Evidence can veto. Contracts can propose classes, landing by consensus. Conditions test value states (is conflicted, is confirmed), so contracts can cascade, and a contract may abstain.
  58. Facets declare agree-by for consensus; class lines take when; completeness is a 0–1 measure; templates gain ?? and ?; a portable shape and share-by-link offers.
