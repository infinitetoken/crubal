Facets v2.0: stable IDs and version control

Design brief, Oct 13, 2026. Written after your Unitizer facet notes and the facet-design discussion page. It builds on docs/v2-model.md (Sept 29), whose question 2, "key ids", was left for later; this is that later. The approach is pragmatic: give every facet an identity and a history on top of today's data, without rewriting the 425,850 products and 366,951 units that already hold facet values.

1Why now

Every inconsistency in your notes traces back to the same gap: a facet has no single, stable identity and no record of how it changed.

  • The name is the identity. A facet is its text key (videoCodec). Product values, 218 template placements and about 20 database functions all key on that name, so renaming is a data migration, not a label edit.
  • The type lives in two places. The dictionary entry has a type, and each template placement keeps its own copy. They drift: 5 facets disagree today (Video Codec, Disc Format, HDR Formats, Aspect Ratio, Included), so screens guess.
  • No history. Changing a definition overwrites it. There is no "what was this yesterday", no undo, and no way to tell which products were written under the old shape. The decision log (22 entries) and recast jobs record some actions, not the definition itself.
  • Breaking changes are silent. Turning text into a choice list, dropping a value or lowering "pick up to" changes what existing values mean, with nothing forcing the stored data to follow.
  • No rules per type. Choice lists draw three ways, dates are all-or-nothing, 25 facets have no type at all.

2Goals and non-goals

Goals

  • Every facet has a stable ID that never changes, plus a free label you can rename.
  • Every change to a definition is a new version: who, when, why, and what changed.
  • One source of truth for a facet's definition; templates only place it.
  • A breaking change cannot go live until the stored data has been converted to match.
  • One rule per type, so a facet draws the same everywhere (the type rules in section 5).

Non-goals (for this brief)

  • Re-keying 425k products' stored values by ID. Values stay keyed by the facet's machine key, which simply stops changing.
  • The entity registry for values (works, people, companies) from v2-model §3. Value IDs here cover choice-list values only.
  • Per-product version stamps on every stored value.
  • Changing how templates stamp (they still stamp, not subscribe).

3The model

Three things, each with one job:

ThingWhat it isExampleChanges?
FacetThe identity. A short public ID, a machine key (where values are stored), a label, aliases (other spellings).F-7KQ2 · key videoCodec · label "Video codec" · aliases "codec", "Video Format"ID and key: never. Label and aliases: freely.
Facet versionAn immutable snapshot of the definition: type, how many (N), values, precision, unit, range, caption, description, where it is collected by default.F-7KQ2 v3: choice list, pick 1, MPEG-2 · H.264 · VC-1 · HEVC · AV1Never edited. A change makes v4.
PlacementWhere a template puts a facet, and only what is true of that spot: order, parent module, collected on product or unit, gates, the photo frame.Optical Disc places F-7KQ2, collected on the product, after Disc formatYes, per template. Never the type or the values.
The pragmatic key. Today's text key (source_path) becomes the machine key: frozen once assigned. That keeps every stored value, every SQL function and every filter working unchanged. A rename changes the label only. Spellings from imports become aliases (the existing canonical_source_path column is the start of this; no facet uses it yet). The short public ID (F-…) is what people and notes refer to, like CashierFu IDs for products.

Choice-list values get IDs too

Each value of a choice list becomes a row with its own short ID, a machine value (what is stored), a label and aliases. "16x9", "16:9" and "Widescreen" become one value with two aliases. Renaming a value's label changes nothing stored. The existing facet_value_curation table (579 rows, already holding aliases) becomes this.

4How versions work

  • Draft, then publish. Edits go into a draft of the next version. Nothing changes on any screen until you press Publish. One draft per facet at a time.
  • Every publish is recorded: version number, who, when, a one-line reason, and the exact differences from the last version.
  • Each change is classed as safe or breaking, worked out from the differences, not chosen by hand:
ChangeClassWhat Publish does
Caption, description, label, icon, an aliassafeGoes live at once.
Add a choice-list value; raise "pick up to N"; widen date precision (Year → Any)safeGoes live at once. Existing values stay valid.
Remove or merge a value; lower N; narrow precision; change the type; change the unitbreakingOpens a migration: shows how many products and units hold values, every distinct value, and a "becomes" column to map each one (the recast tool, already built). The version goes live when the migration finishes.
Retire the facetbreakingHidden from new collection; values kept and readable; can be restored.
  • Revert is "publish an old version again" as a new version, with its own migration if going back is breaking.
  • Placements follow the current version. They carry no copy of the type or values, so the dictionary and templates cannot disagree again.

6Screens

A facet's page

  • Header: label, F-7KQ2, key, type, current version.
  • Definition: the current version, read-only, with "Edit (new draft)".
  • Draft: the editor; a live preview of the control; Safe / Breaking shown as you edit; Publish.
  • History: every version, who, when, why; diff any two; Revert.
  • Used by: templates that place it, products and units holding values, value counts.

Publishing a breaking change

  • The impact first: "317,561 products hold a value."
  • Every distinct stored value, with a "becomes" picker (the recast mapping table).
  • Run: a job converts in slices with a progress bar; the version goes live at the end.
  • Values the map leaves out are listed, never silently dropped.

Templates

  • The canvas places facets by ID and edits placement settings only.
  • The type and values shown on a placed facet are the current version's, read-only, with a link to the facet's page.

Everywhere else

  • Notes, the decision log and the Queue refer to facets as F-7KQ2 videoCodec.
  • The Unitizer and Editor show a small "v3" in a facet's info panel.

  • No product or unit rows are rewritten by the identity or version steps. Only a breaking change converts values, through the recast job that exists today.
  • The existing "placement-only" list in the code (PLACEMENT_OVERRIDE_KEYS) already names which settings belong to a placement, so the split is mechanical.
  • Version 1 of every facet is written from today's dictionary entry. The 5 disagreements are listed for you to settle in Phase 0, never guessed.

8Phased plan

Each phase ships alone and leaves the system working.

0
Clean the data. Settle the 5 type disagreements, give the 25 untyped facets a type, write Video Codec's values. A decision list for you, applied with your OK.
1
IDs and history. public_id on every facet; facet_version with v1 from today; freeze the machine key (renames edit the label). The facet page shows ID, version and History. Nothing else changes.
2
One source of truth. Placements stop carrying definitional settings; every screen reads the type and values from the current version. The disagreements become impossible.
3
Draft, publish, migrate. The draft editor with live preview, the safe/breaking check, Publish, and breaking changes opening the recast migration. Revert.
4
Type rules. Choice lists as bubbles with N; date precision; the rest of section 5, drawn from the version.
5
Value IDs. Choice-list values as rows with IDs, labels and aliases; merges and renames through versions.

9Risks and costs

  • About 20 database functions key on the facet name. Freezing the name as the machine key keeps them working; that is why the key does not become a uuid.
  • The census and enrichment read definitions. They move to reading the current version; the shape of the definition stays the same, so the change is a read path, not a rewrite.
  • Breaking changes on big facets take time (aspect ratio has 317,561 carriers). The recast job already runs in slices with progress and has run on production.
  • Two machines. Phase 2 touches the template editor and every render path; it needs the build machine idle or a clear split.
  • Scope creep toward v2-model's entity registry. Value IDs here stay inside one facet; cross-facet entities (one "Warner Bros." for studio and publisher) are a later step.
