A facet language: one small syntax for keys, values and their definitions

Working draft for discussion, Oct 13, 2026. Before building facets v2.0, you asked to learn from schema.org and Wikidata, keep it very simple, write it two ways (spelled-out keys, or short symbols), let facets and values carry their own definitions, track which class or module shaped each facet, handle aliases, and see whether CRUBAL still fits. Working name below: CRUBAL 2. The name is yours to pick.

1What the three systems teach

schema.org

  • Types in a tree: Thing → CreativeWork → Movie. A thing can have several types.
  • Properties name what they apply to and what they hold (actor: on a Movie, holds a Person).
  • Plain data types: Text, Number, Date, Boolean, URL.
  • Enumerations as named members (ItemAvailability → InStock).
  • QuantitativeValue: a value with a unit code.
  • sameAs links a thing to the same thing elsewhere; Role adds detail to a link (actor + character name).

Take: the class tree, and the vocabulary search engines read. We already write schema.org for Google; every facet should say which schema.org property it is.

Wikidata

  • Everything has an ID: items Q…, properties P…. Names are labels, with aliases.
  • A statement = property + value + qualifiers (detail) + references (where from) + rank.
  • Each property has a data type: item, text, quantity with unit, URL, external ID with a link template, media file.
  • Time carries a precision: year, month or day. This answers the date question.
  • Two kinds of empty: "some value" (exists, unknown) and "no value" (does not apply).
  • Constraints as data: allowed values, one value only, format pattern.
  • "instance of" and "subclass of" make the tree.

Take: IDs and aliases at both levels, date precision, the two kinds of empty, qualifiers, external IDs with link templates, constraints as data.

CRUBAL (ours, 2026)

  • Key/value pairs with a firewall between a key's definition and its values.
  • Facet · Module · Housing: a facet points at a reusable shape (scale, boolean, input, log, price); modules group facets in order.
  • Values nest (a disc inside a case inside a set).
  • Reference triad: ref (one of our products), url (a web page), query (computed).
  • Provenance: where a value came from (seller, AI, import, template).
  • Key known, value unknown: an empty key is valid and is the fetch list.

Take: all of it. Our metadata documents are still CRUBAL key/value pairs. What CRUBAL lacked was IDs, versions, aliases, precision, influence tracking and a written syntax.

Does CRUBAL still hold? Yes, as the base. Every product and unit already stores CRUBAL-style key/value pairs, and its firewall, housings, nesting, reference triad, provenance and null floor are all in the live system under other names. CRUBAL 2 is CRUBAL plus a written syntax and the Wikidata and schema.org pieces it was missing. Nothing about it requires changing how values are stored.

2The two methods

Every statement can be written spelled out (keys and words) or in symbols (one compact line). Both read into the same definition, so you can type whichever is faster and the system can print either back.

Spelled out (the key method)

facet videoCodec "Video codec"
  type choice, pick 1
  values MPEG-2, H.264, VC-1, HEVC, AV1
  aliases codec, "Video Format"
  same as schema:encodingFormat
  from Optical Disc

In symbols (the function method)

videoCodec{MPEG-2|H.264|VC-1|HEVC|AV1}*1
  ~codec ~"Video Format"
  =schema:encodingFormat <OpticalDisc

Values on a product are one line each either way: videoCodec: H.264. Any key can be replaced by its ID: F-7KQ2: H.264.

5Tracking class and module influence

Every facet on a product records which class or module put it there, and how each one shaped it. The tail < says who introduced it; a class that narrows a facet writes the narrowing beside its own name.

# the dictionary says what a format can ever be
format{DVD|Blu-ray|4K|HD-DVD|VHS|LaserDisc}*+

# classes narrow it; each narrowing is recorded with the class
class OpticalDisc <VideoRelease
  format{DVD|Blu-ray|4K|HD-DVD}            # narrows: no tape
  videoCodec{MPEG-2|H.264|VC-1|HEVC|AV1}*1

class Movie
  !title$  releaseDate@any  runtime#min  cast(person&Person character$)*+

On a product, each value can be traced back:

format: Blu-ray        # allowed by: dictionary → narrowed by OpticalDisc
videoCodec: H.264      # introduced by OpticalDisc
runtime: 97min         # introduced by Movie

The rule from the live system holds: a class may only narrow what the dictionary allows (fewer values, a lower "pick up to", a tighter precision), never widen it. The language makes that check mechanical.

6Aliases

  • Key aliases (~): other spellings of a facet. runtime#min ~Runtime ~runtime_min ~"Run time". An import using any alias lands on runtime.
  • Value aliases: inside a choice list, = joins spellings to one value. aspect{16:9=16x9=Widescreen|4:3=Fullscreen}.
  • IDs never change; labels and aliases are free to edit, and a rename is just a new label.

9Transport and map: every system is a contract

    
The language is not only for describing products. Its main job is transport: moving data between systems that each keep their own fields. Today every pair of systems needs its own hand-written bridge (Unitizer → label printer, product → eBay, location → Shippo, product → Google). Ten systems that all talk to each other need up to 45 bridges, and the number grows with the square of the systems. With facets in the middle, each system declares one map to the facets, and ten systems need ten maps.

    


# today: N² — every pair wired by hand

Unitizer ──→ eBay

 … one bridge per pair


# v2: N — each system maps once, to facets

A contract is a system declaring its variables and its map

    
Every functional system (a printer, a shipping service, eBay, the pricer, a screen) publishes one contract in the same language: what it needs, what it gives back, how each of its own fields maps to a facet, when it may run and who may run it. That is the "smart contract": a declaration the system enforces, so a caller that satisfies it can use the system without knowing anything else about it.


contract Shippo.label
  needs  !shipFrom(line1$ city$ state$ zip$)  !shipTo(line1$ city$ state$ zip$)  !parcel.weight#oz
  gives  trackingNumber$  label^  postage#usd
  map    address_from.street1 <- shipFrom.line1
         address_from.zip     <- shipFrom.zip
         mass_unit "oz", weight <- parcel.weight      # the language converts lb → oz
         tracking_number      -> trackingNumber
  when   order.status = paid
  who    seller

contract Location                               # an object maps its own columns once
  map    location.line1 <-> shipFrom.line1   location.zip <-> shipFrom.zip

contract eBay.listing
  needs  !title$*80  !format  !condition  price#usd
  map    Title <- title
         "Format" <- format { DVD => "DVD" | Blu-ray => "Blu-ray" | 4K => "4K UHD Blu-ray" }   # a value map
         ConditionID <- .grade { NM => 2750 | VG => 4000 | G => 5000 }

    
Shippo and Location never mention each other. Both map to shipFrom; a fourth location type, or a second carrier, is one more contract and nothing else changes.

Machinery is the same thing, inside our own house

    
    
      
  • Machinery facets already exist: settings Classes are "a roster that directs a service" (rack slots, printers, the unit series). In the language they are contracts whose variables are settings: contract LabelPrinter needs !sku$ price#usd barcode$ title$*32 gives printed?.
    • 
      
  • The map is data, not code. Today facet_curation already says where a facet lives and which side is the truth (residence, residence_ref, flow), for products only. Contracts are that idea for every system.
    • 
      
  • Checking is free. Before a system runs, the contract tells you what is missing ("eBay needs Format; this product has none"), which is the completeness check the dictionary already does, aimed at a destination.
    • 
      
  • The UI assembles itself. A screen that runs a contract shows its needs, using each facet's own widget. No hand-built form per destination (your "build the engine, not the example" rule).
    • 
      
  • Versions apply. A contract is versioned like a facet; a breaking change to eBay's contract (a renamed specific) is one map edit, seen and dated.

10Lining up with UCP (Shopify + Google, Jan 11, 2026)

    
The Universal Commerce Protocol (ucp.dev) is the published standard for systems and AI agents buying from any store. It already does, for commerce systems, what section 9 proposes for facets: every party publishes a declaration of what it can do, the two sides compare declarations, and only the overlap is used. We should speak it, and borrow its rules.

    

      
UCP doesWhat it means for us

      
        
A profile at /.well-known/ucp: each business and each agent publishes its services and capabilities, each with a link to its schema.Our contracts. Every system publishes one declaration; ours can be served the same way so outside agents read our catalog without custom work.

        
Reverse-domain names: dev.ucp.shopping.checkout, com.vendor.…. Whoever owns the domain owns the name; no central registry.Facets and contracts get an owner prefix: com.mediaencyclopedia.videoCodec. Ours, eBay's and schema.org's sit side by side without clashing. Inside our own system the short form videoCodec stays.

        
Date versions (2026-01-11) on the protocol and on each capability separately.Facet and contract versions dated the same way: videoCodec@2026-10-13, each facet on its own clock.

        
Extensions name the capability they extends and add fields to it; schemas compose by stacking.Exactly our class/module influence: a class extends another and adds or narrows facets. Same word, same rule.

        
Negotiation: keep only what both sides list, pick the newest version both support, drop extensions whose parent is gone.The contract check: what a destination needs, intersected with what a product carries, shows what is missing before anything runs.

        
A reserved ucp envelope on every response saying which version and capabilities were used.Everything we send out can say which facet versions shaped it.

        
Catalog products have typed slots (title, price in minor units, variants, options, barcodes, categories with a taxonomy) and a free metadata bag for everything else.UCP has no typed attribute system: runtime, region, codec, condition would all land in an untyped bag. That is the gap our facets fill. We publish them as an extension, com.mediaencyclopedia.shopping.catalog.facets extends dev.ucp.shopping.catalog.

      
    

    
What changes: contract names take a reverse-domain owner, versions are dates, "from" (<) is spelled extends to match UCP, and our catalog goes out as a UCP catalog plus our facets extension. The symbol language stays; UCP is the envelope it travels in. (UCP itself doesn't use the words "Ecommerce 3.0" or "smart contract"; its "capability declaration" is the same idea.)

  


  

    
11The math: how values combine

    
Every time two things meet, a rule decides the result: a class meets the dictionary, a second stamp meets the first, a disc meets the case it sits in, a unit meets its product, a filter meets another filter. Today that rule is implied and differs by place. In v2 each facet declares how its values combine, and there are only three kinds.

    

      
Additive
Contributions pile up.
    
        
  • Sets union: Movie + Blu-ray stamps give format DVD ∪ Blu-ray; cast from every source joins.
    • 
        
  • Numbers sum: a box set's weight = the discs + the case; total runtime = each disc's runtime.
    • 
        
  • Counts add: units on hand.
    • 
      

      
Deductive
Each contribution takes something away.
    
        
  • Sets intersect: dictionary → class → product may only narrow the allowed values (the rule we already have).
    • 
        
  • Numbers subtract: a price minus a deduction per fault; a grade minus missing parts.
    • 
        
  • Worst wins: a set's condition is its worst part (min); sealed only if every part is sealed (and).
    • 
      

      
Independent
Contributions don't touch each other.
    
        
  • Each facet keeps its own value: region says nothing about codec.
    • 
        
  • Independent axes multiply: 3 formats × 2 regions × 2 editions = 12 possible variants (the variant matrix).
    • 
        
  • Filter counts can be counted one facet at a time; dependent facets (gated ones) need counts taken together.
    •

In the language it is one more tail mark: weight#lb +sum, format{…}*+ +join, .condition{NM|VG|G|F|P} +worst. Spelled out: combine sum.


    
Why the math matters

    
    
      
  • Order stops mattering. join, sum, narrow, worst and best give the same answer whatever order things arrive in, and applying the same stamp twice changes nothing. Only replace depends on order. Today stamps are order-dependent everywhere; with declared rules, only replace facets are, and the system can warn exactly there.
    • 
      
  • Rollups write themselves. A product's value from its units, a set from its discs, a container from its contents: each is the facet's combine rule run over the parts. No per-screen code.
    • 
      
  • Merges are safe. Two people editing, an import landing over hand edits, AI filling gaps: with order-free rules the results meet cleanly. This is the same math that lets offline apps sync without conflicts.
    • 
      
  • Transport keeps meaning. A contract can say "eBay's weight = sum of parts in oz" or "Condition = worst part, mapped to eBay's ID". The rule travels with the facet.
    • 
      
  • Filters count correctly. Independent facets get fast per-facet counts (what facet_value_stats does today); facets marked dependent tell the filter rail it needs joint counts.
    • 
      
  • Breaking changes become visible. Changing a facet's combine rule (join → replace) changes every rolled-up value, so it is a breaking version change.
    • 
    

  


  

    
12Where it fits with the v2.0 brief

    
    
      
  • A facet version is one definition statement. Its symbol line is its fingerprint: two versions differ exactly where their lines differ, and the safe/breaking check reads the difference (more values: safe; fewer: breaking).
    • 
      
  • IDs (F-…, V-…) can stand in for any key or value.
    • 
      
  • Templates are classes written in the language: a list of facet lines with narrowings, plus placement settings.
    • 
      
  • schema.org output for Google is generated from each facet's =schema: link, not hand-mapped.
    • 
      
  • Imports and AI read and write the language; aliases and value shapes do the matching.
